❯ Enter = send · Shift+Enter = newline

Pros

  • Highest visibility — the suggestion sits exactly where the user's eye already is (above the input).
  • Editor is the primary surface, not an afterthought — encourages review before Send.
  • Rationale is inline, not tucked behind hover, so the "why this?" is answered without asking.
  • Handles multi-line prompts and long rationale gracefully.

Cons

  • Steals ~120 px of vertical space whenever a session is idle — dense on small windows.
  • Two edit surfaces (card + terminal input) may confuse "which one am I typing in?".
  • If the user just wants to type freely, the card has to be dismissed first.

Pros

  • Zero extra chrome — no card, no strip, no toast. The input line does the work it always did, just prefilled.
  • Muscle-memory keys: Tab / Enter / Esc match how editor completions already feel.
  • Sends immediately when the user hits Enter — one keystroke fast path.
  • Rationale + confidence live in a slim toolbar below; low visual weight until you look.

Cons

  • Ghost text is harder to review than an inline card — the eye may skim over it and hit Enter without reading.
  • Multi-line proposals wrap awkwardly in a single-line input; may need a "pop out to editor" affordance.
  • If the user starts typing without hitting Tab first, we have to decide: replace ghost with typed chars, or reject ghost silently?
  • Screen readers need extra ARIA to announce "suggestion available" and its content.

Pros

  • Non-intrusive baseline — the terminal stays exactly as it was; the chip sits over dead space.
  • Zero interference with typing — the input line is untouched until the user chooses to engage.
  • The pulse animation on new suggestions gives a soft "hey, something new" without demanding attention.
  • Two-tier UX — glance (chip) vs. commit (expanded panel) — matches how the user actually reads suggestions.

Cons

  • Hidden by default — users may miss it, especially with a very tall transcript.
  • Extra click to reach the editor; friction if the user always wants to review + edit.
  • Overlay can obscure the tail of the agent's last message on short terminals.
  • Needs a "keyboard-first" story (e.g. Alt+M to expand) so power users aren't mouse-locked.

Pros

  • Reads naturally as part of the conversation — "the agent stopped, Maestro spoke, now it's your turn".
  • Scrollable — a stale suggestion doesn't clutter the input area; you can scroll past it later.
  • Doesn't fight the terminal input at all — user can type independently in the bar below.
  • Rationale + assumptions can expand generously without eating a chrome budget.

Cons

  • Sits inside the transcript view — if that view has virtualization / auto-scroll on tail, it moves with new content.
  • "Send" from a block that's above the input feels off — visual + input focus split.
  • Requires a "load into input" hand-off flow so the user can polish the suggestion in the bar first.
  • The block persists in scrollback after send — either becomes noise history, or needs an "archive on send" step.
